## 4. Design

### 4.1 Alarm files (as found on staging, 2026-11-06)

- One file per UTC day **that had an alarm** (84 files on CDP1 since 24 December 2025), CSV with the header
  `DD/MM/YYYY HH:MM:SS,Site Identifier,Alarm Name,Type,State,Active,Message`, CRLF line ends, trailing tabs.
- Each row is a **change**: an alarm raised (`Active` true) or cleared (`false`), with the AWOS state `pending` or
  `acknowledged`. CDP1 has 784 rows and 75 names in 11 months.
- The message may contain commas: the first six fields are split, the rest is the message.
- **As built:** the CDPs do *not* write the same rows. Each runs its own alarm detection and logs the same change
  up to a minute or two apart (only 126 of 1,265 rows matched exactly; the widest pair seen was 85 s apart). Each
  CDP's rows are stored as read, keyed on (CDP, time, name, type, state, active, message), so re-reading a file
  adds nothing; rows of the same content from different CDPs within **2 minutes** of each other are shown as one
  change with the CDPs that logged it (578 of 622 CDP2 rows have a CDP1 row within 2 minutes).
- A file dated `19700101` holds rows timed 1970 (a clock reset). Rows before the system's coverage start, or more
  than 2 minutes in the future (E5), are skipped and counted as parse warnings.

### 4.2 Alarm model

- `alarm_event`: one row per change (above), never edited.
- `alarm_name`: one row per name with its site and sensor (or "station", or "unmapped"), seeded per D4, editable in
  Admin → Alarm mapping, audited. Mapping is applied when reading, so changing it re-maps the whole history at once.
- **As built:** `alarm_source_row` holds each CDP's rows; `alarm_event` (the merged changes) is rebuilt per name
  whenever a new row of that name arrives.
- **Active (D8, Product Owner 2026-11-06):** the AWOS logs raises far more reliably than clears. Most alarms are
  raised again with no clear in between, and on 6 November 2026, 47 of the 75 names had "active" as their latest
  change, some since December 2025 (the three `DCP*_Missing` alarms were raised on 2, 3 and 5 November and never
  cleared in either CDP's file, while data kept flowing). "The latest change says active" alone would show 47
  active alarms. So an alarm is **active** while its latest change says active **and is at most 24 hours old**;
  older ones are listed separately as "no clear logged" and are not counted in the Problems panel. **Raised** = an
  active change that is not an acknowledgement of an alarm already active; "since" is the latest raise. The AWOS
  state is shown as reported.
- Ingestion follows the 1-minute reader: each CDP on its own time-limited threads, files re-read only when their
  size or time changed, today's and (for 2 hours) yesterday's file in every cycle, status per source on the health
  page. Reprocess jobs gain a choice of sources (1-minute, alarms, reports; FR-ING-010).

### 4.3 Report files (as found on staging)

- `reports/METAR.<date>.log`, `METREPORT.<date>.log`, `TAF.<date>.log`: three header lines, then each report with
  its log time `YYYY/MM/DD HH:MM:SS` (UTC). METAR lines end with the runway in use, `(04)`.
- METAR and MET REPORT: one report per line. TAF: a bulletin line (`FTID31 WIDN 050400`) followed by the report
  over several lines, ending at `=`.
- CDP2 logs only some reports (12 of 58 METAR lines on 5 November): it seems to log only while it is the active CDP.
  Lines both CDPs have are identical, so a report is stored once, keyed on (type, log time, text), with its CDPs.
- About 120 reports a day. The same report sent twice seconds apart is kept twice: the archive shows what was issued.
- **Found on CDP1 (320 days, checked 2026-11-08):** 15,467 METAR and 1,024 SPECI (about 51 a day), a MET REPORT
  every half hour plus 2,720 SPECIAL, and about 3 TAF a day (19 `TAF AMD`). Files also exist for SYNOP, ATIS, AFTN,
  CLIMAT, CREX, BUFR and AMHS (not read, D6).
- Each METAR and MET REPORT line ends with the AWOS's own notes in brackets after the `=`: the runway in use,
  `(04)`, and for a SPECI or SPECIAL the reason, e.g. `(visibility decrease through 5000)`,
  `(thunderstorm onset)`, `(manually created condition)` (475 of the SPECI). They are stored apart from the report
  text and shown as labels; the text itself is shown and copied exactly as issued (FR-RPT-004).
- The same METAR is sometimes logged twice about a minute apart: both are kept (they were both issued).

**R3.2 as built (screens approved 2026-11-08):**

- **The CDPs log reports separately**, as they do alarms: of 3,091 CDP2 METAR lines in 60 days only 839 match a
  CDP1 line exactly, 2,146 have the same text at another time (all within 117 s). So, as for alarms,
  `report_source_row` keeps each CDP's lines as read (unique per CDP, type, log time and text), and `report_entry`
  holds one row per report: type (`metar`, `metreport`, `taf`), kind (METAR, SPECI, MET REPORT, SPECIAL, TAF,
  TAF AMD, TAF COR), the earliest log time, text, notes, runway, TAF bulletin heading and the CDPs. Copies with
  the same text from different CDPs within 2 minutes are one report; it is rebuilt per text when a new line of
  that text arrives. Never edited.
- Different texts for the same time are different reports and both are kept (1 November 2026, 21:30–23:30: CDP1
  logged `AUTO` METARs, CDP2 others).
- The worker reads today's and (for 2 hours) yesterday's three files per CDP, like the 1-minute files. The history
  from 24 December 2025 (about 950 files per CDP) is loaded once by a reprocess job with the source "reports",
  started by an Admin after the deploy (FR-ING-010: a deploy never starts a reprocess by itself).
- API (public): `GET systems/{code}/reports/latest` (newest six of each type), `GET systems/{code}/reports?day&type`
  (one UTC day, with each type's count), `GET systems/{code}/reports/search?type&from&to&q&offset&limit` (text in
  the report or the AWOS's notes, at most 31 days, newest first).
- Screens: one public page, *METAR, MET REPORT and TAF*, linked from the system menu, with three tabs: Latest (each
  type's newest, copyable, with the five before; METAR and MET REPORT say so when the newest is older than 40
  minutes), Daily archive (previous/next day, report kind with counts, only specials or amendments), Search.

### 4.4 Monthly PDF (R3.5, as built)

- `POST systems/{code}/exports/monthly-report` with `{"month": "YYYY-MM", "lang": "id" | "en"}` (Viewer, CSRF
  header), answered with the PDF, `SIMOLA_<system>_<YYYY-MM>_<lang>.pdf`, `Cache-Control: no-store`. Generated
  on request and not stored.
- Checked in this order: role and CSRF, the month (`validation_error`; `month_in_future`), the system, the
  per-person limit shared with the CSV files (ten a minute, `too_many_exports`), then **one report at a time on
  the whole server** (a Postgres advisory lock across both API workers, `report_busy`; a dying worker frees it
  with its connection). The audit entry `export` / `monthly-report` with system, month and language is written
  once the PDF is ready, so a refused or failed report is not counted.
- **The data** (`simola/report/gather.py`) comes from the functions behind the dashboard's routes, called with
  one `now`: `/kpis`, `/matrix` by day, `/outages` for `ola` (15 longest) and `sla`, `/data-quality` as a
  signed-in user, the alarm history's change count and raised-per-day counts plus the raised count per alarm
  name, and calibration status **as it stood on the month's last day** (today while the month runs): records
  dated later are left out and a certificate validated later shows as pending, so a past month's report is the
  same whenever it is made. The integration test asks the API for the month and compares (FR-KPI-001, U6).
- **The pages** (A4, `simola/report/templates`, Jinja2 with autoescaping, WeasyPrint 70): cover with the five
  headline figures, period and minutes counted, data coverage (days with nothing to count are named, E11; a
  running month says up to when), generated at/by, definitions version, contents and a sign-off box ("Prepared
  by" / "Acknowledged by, Head of Station"); 1 KPI summary and network reachability with probe coverage; 2 sites
  and sensors; 3 daily SLA/OLA chart (SVG, axis as close to 100 % as the lowest day allows, the display
  thresholds dashed) with the daily table, then the colour grid of every row by day; 4 the 15 longest outages
  with cause and detail, lost minutes by cause and a line on SLA; 5 alarms raised by type and per day, the ten
  most raised; 6 data quality; 7 calibration with days left; 8 the formulas. Eight pages for a normal month.
- Words follow the dashboard's (a unit test compares the shared ones with `frontend/src/i18n`); numbers use the
  language's marks (id 44.640 and 99,84); times are UTC as on the dashboard.
- Fonts: Inter 4.0 (Regular, Medium, SemiBold, Bold) cut to Latin and a few symbols, 360 kB, OFL, in
  `simola/report/fonts`. While rendering, the URL fetcher serves only those files and refuses every other
  address, so text in the data can never make the server fetch anything. The API image adds Pango and HarfBuzz;
  CI renders a PDF in the unit tests and runs the renderer's self-test inside the built image.
- Rendering runs in a thread so the API keeps answering. Sample data: 3–5 s for a month on the development
  machine; measured on staging with the full history at deploy.
- Exports page: month (from the month the data starts to this month, last month by default), language, file
  name, "Drawing the report… N s" while it is made, notes for a running month and for the first month (E11),
  and the refusals explained on the page. In sample mode the download is a one-page placeholder PDF.

### 4.5 CSV exports (R3.4, as built)

- UTF-8 with a byte-order mark (Excel reads ° and Indonesian text right), a header row, UTC times in ISO form,
  decimal point, units in the headers; text cells starting `= + - @` get a leading apostrophe, as the audit export
  does; numbers are written as they are. Streamed a day at a time, so a 31-day 1-minute file does not sit in memory.
- Every row ends with `definitions_version` and `generated_at_utc` (FR-KPI-008). They are columns rather than a note
  above the header, so the file opens and re-imports cleanly.
- `GET systems/{code}/exports/{kind}.csv?from&to…` (Viewer), file name `SIMOLA_<system>_<kind>[_<site>]_<first
  day>_<last day>.csv`:
  - `daily` (≤ 366 days): one row per UTC day and scope (system, cdp, site, component) with `expected_min`,
    `valid_min`, `missing_min`, `availability_pct`, and for CDPs `reachable_min` and `probed_min`. The counts are the
    engine's daily counts, so the sums are the period's figures (U7; integration test against `/kpis`).
  - `minutes` (`site`, ≤ 31 days): one row per minute from the coverage start up to now: `time_utc`, `cdps` (the
    CDPs whose files had the minute), then per sensor `TYPE.status` (the minute map's letters spelled out: valid,
    field_missing, no_data, flagged, detection, not_counted) and `TYPE.FIELD (unit)`.
  - `alarms` (`type`, `scope`; ≤ 366 days): every change, oldest first, with `change` raised, acknowledged or
    cleared.
  - `quality` (`records=flags,detections`, `all`; ≤ 366 days): one row per active flag and sensor, one per
    detection (confirmed only unless `all`), with `counts` true when it takes minutes out of the figures.
- Checked before anything is written: the role, the period, the site; then at most ten files a minute per person
  (API-10, `too_many_exports`); then the audit entry `export` with the parameters. A refusal is a JSON problem the
  page explains; the page fetches the file and hands it to the browser.

### 4.7 Screens

- **Alarms** (Viewer): active list, history with filters and a per-day count chart; site pages list the site's
  active alarms; the day view marks alarms next to the minute map.
- **Admin → Alarm mapping**: every name, its site and sensor, unmapped first.
- **Reports** (public): latest METAR, MET REPORT and TAF; a day's archive by type; search.
- **Data quality** (public, suspects for signed-in users) and **Definitions** (public).
- **Exports** (Viewer): month and language for the PDF; period and kind for each CSV.
- Indonesian and English for every new text; phone layouts checked as in R1 and R2.

### 4.9 Data-quality summary and definitions (R3.3, as built)

- `GET systems/{code}/data-quality?from&to` (public, at most 93 days like the outage list): for every sensor, the
  minutes the outage list puts under "flagged" and "confirmed detection", with the flags and detections behind
  them and their reasons (flag reason, detection rule type); totals by reason; `pending_suspects` only for
  signed-in users, `null` for the public (D7). Built from the same engine as the outage list, so the minutes are
  equal by construction (R3.3 acceptance).
- `GET definitions` (public): the definitions version (`1.0`), the day it applies from (the coverage start) and
  where it is written down (PRD v1.1 §7.3.1). The page shows the formulas in plain words, the mandatory fields in
  force (from the registry), the grace and the colour thresholds (from the settings). Exports and the monthly
  report will carry the version.
- Screens: *Data quality* and *Definitions* in the system menu; the footer links to the definitions on every page.
- The pending suspects are those overlapping the period (signed-in users only).
- With R3.3 the alarm reader no longer reads every alarm file when the worker starts: like the report logs, it
  reads today's and yesterday's files, and the history is read by a reprocess job (FR-ING-010).

## 6. Risks

| Risk | Mitigation |
|---|---|
| The meaning of `State`/`Active` is inferred from the files, not documented | Shown as reported; "active" uses only `Active`; you check a few known events in R3.1's screenshots |
| A report format the samples did not show (TAF amendments, corrections, empty days) | Parse tests on every day of the 11-month history before R3.2 ships; unknown lines counted, never dropped silently |
| WeasyPrint's size and memory on the shared 4-CPU host | Rendered one at a time; measured in R3.5; the PRD's alternative (headless Chromium) is heavier, not lighter |
| R3 deploys during the December live run (D2) | No deploy in the last two days of December; the recount checks every day either way |
