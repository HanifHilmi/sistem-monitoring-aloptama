# SIMOLA R2 design: access and data quality

**Status:** D1–D4 decided by the Product Owner on 2026-11-05; D5 is the PRD's default. Nothing in it is built yet.
**Source:** PRD v1.1: §5.4 (roles), §7.2 (registry), §7.3 (KPI), §7.5 (data quality), §7.10–7.12 (access,
administration, audit), §8.3–8.4, §11.6, §12.4, §15. This design adds only what the PRD leaves open.

R2 lets technicians **log in, mark bad data, and maintain the station's records**, with every change audited and
the figures following within minutes. The public keeps the R1 view.

## 4. Design

### 4.1 Accounts and sessions (R2.1)

- **Tables:** `app_user` (username, display name, optional email, role, active, password hash, must-change flag,
  failed-login count and lock-until), `user_session` (hash of the token, user, created, last seen, expires, IP,
  user agent). The token itself lives only in the cookie.
- **Login:** `POST /api/v1/auth/login` checks the password (Argon2id, `argon2-cffi`), creates a session and sets
  `simola_session` (HttpOnly, Secure, SameSite=Lax) and a CSRF cookie. The same error for an unknown user and a wrong
  password. `POST /auth/logout` deletes the session row, so a copied cookie stops working.
- **CSRF:** double-submit token. Every POST, PUT, PATCH and DELETE must send the CSRF cookie's value in a header.
- **Brute force:** 5 failures in 15 min lock the account for 15 min; a per-address limit on login attempts. The
  client address comes from the `CF-Connecting-IP` header, trusted only when the request arrives through the
  proxy.
- **Passwords:** at least 12 characters, checked against a bundled list of common passwords; an Admin reset sets a
  temporary password that must be changed at the next login.
- **Bootstrap:** `simola create-admin --username <name>` in the worker container prompts for a password; it refuses
  if an active Admin exists.
- **Authorization:** one dependency per router declares the minimum role; the permission matrix test (§4.8) calls
  every endpoint with each role. The last active Admin cannot be deactivated or demoted.
- **Role-shaped responses:** R1's public response shaping becomes one serializer policy with three levels (public,
  Viewer, Admin). The internal health API moves from "protected by Cloudflare Access" to "Viewer or Admin".

### 4.2 Audit (R2.1)

- `audit_event` (time UTC, actor, action, entity type and id, before and after as JSON, source address), written
  **in the same transaction** as the change it records.
- **Append-only in the database, not only in the code:** the application role loses UPDATE, DELETE and TRUNCATE on
  this table (R1's role setup grants all four on every table), and a trigger rejects updates and deletes from any
  role except the owner. A test proves the application cannot change or delete an entry.
- Viewer page for Admins: filter by date, actor, action and entity; CSV export (itself audited).

### 4.3 How flags and detections change the figures (R2.3, R2.4)

R1 decides "component valid in this minute" in **one place**: a SQL condition (mandatory fields present, inside the
in-service period), shared by the KPIs, the matrix, the minute map and the outage list. R2 adds one more clause
there and nowhere else:

```text
valid = mandatory fields present AND in service AND no invalidating interval covers this minute
```

- **Invalidating intervals** = active manual flags + confirmed detections on a mandatory field, per component, kept
  in one table with a time range and a GiST index (`component_id`, `during`). DCP is never in it.
- **After a change** (flag added, edited or removed; detection confirmed, rejected or reversed; mandatory fields or
  in-service period changed): the change and its audit entry are written in one transaction, the affected days are
  marked for recomputation, and the worker recomputes them (already how R1 keeps daily figures). Pages show
  "recalculating" for that scope until it is done. Target: one month within 5 min, full history within 30 min
  (NFR-PERF-005).
- **Outage list:** the reserved causes "flagged" and "confirmed detection" start returning intervals, with a link to
  the flag or detection.
- **Safety net:** with no flags and no confirmed detections the figures must stay identical to R1's. `tools/recount.py
  --daily` on staging must still match every day after each phase.
- **R2.3 as built (screens approved 2026-11-05):** tables `flag` (UTC minute range, reason, note, created / updated /
  removed by and at) and `flag_component`, plus `invalid_interval` (`component_id`, `during` tstzrange, source,
  source id; GiST on (`component_id`, `during`), `btree_gist`) written in the same transaction. The engine loads
  the intervals of a window and adds `NOT (time in range …)` only for components that have some, so without flags
  the SQL is R1's. Decisions: flags cover the past only; a note is required (3–500 characters); a minute already
  lost keeps its cause, so a flag costs only otherwise-valid minutes (U4: 60 valid minutes flagged = 60 lost); one
  flag may cover several components; DCPs cannot be flagged; ranges over 31 days are allowed with a hint to use the
  in-service period; removal is a soft delete. Live component status (top bar, Problems) ignores flags: it is about
  data arriving now.

### 4.4 Rules and detections (R2.4)

- **Tables:** `dq_rule` (field, component type, optional site, type, enabled) with `dq_rule_version` (parameters,
  created by, created at). A change creates a new version; old versions stay for traceability.
  `dq_detection` (component, field, rule version, parameter snapshot, start, end, status Suspect/Confirmed/Rejected,
  decided by, decided at, note).
- **Rule types:** range (min, max), stuck (same value for N or more minutes, optional values to ignore such as 0
  for rain), spike (change larger than X between consecutive valid minutes, optional window). Missing values never
  trigger a rule, and a missing minute breaks stuck and spike runs.
- **Runs:** written as SQL window functions over the minute table, so a month is one query per rule.
  - Incremental: after each ingestion cycle, over the new minutes plus enough earlier minutes to finish a run.
  - Full: on a rule change or reprocess, as a job over the affected range (default: all history).
  - Results are merged into intervals. The same data and rule versions always give the same intervals.
  - A rejected interval is not raised again for the same rule version.
- **Review queue:** filter by system, site, component, rule and date; each row opens the sensor chart around the
  interval; confirm or reject one or many with a note; reverse later (audited).
- **Starting values (OPEN-08):** a report per field from the 11+ months of history (value ranges, longest unchanged
  runs, largest minute-to-minute changes) with a proposed value for each rule. All rules start **disabled** until
  you approve them.
- **R2.4 as built (screens approved 2026-11-05):** tables `dq_rule` + `dq_rule_version` (scope, parameters, on/off
  per version), `dq_detection` (rule version, parameter snapshot, evidence, status, decision) and
  `dq_field_history` (stored statistics, refreshed weekly; a field's whole history takes ~7 s on staging). Rules
  are applied in Python to one field's minutes per site (`simola/dq/rules.py`, pure and unit-tested), a month per
  transaction for history runs (job type `detect`) and the last stuck-length + 2 h every minute in the worker.
  Hits merge into stored detections of the same rule version by overlap (touching for range and spike, and for
  stuck runs of the same value), so a month-by-month run equals a single pass and decisions persist; a suspect that
  no longer fires inside a run's window goes. Confirmed detections on mandatory fields are written to
  `invalid_interval` (source `detection`) and rebuilt after a decision or a mandatory-field change; flags come
  first. Proposed values: range = middle 99.8 % widened by a quarter of the spread; stuck = 2 × the 99.9th
  percentile of unchanged runs (≥ 60 min); spike = 2 × the 99.99th percentile of minute changes, for slow
  fields only. Live component status ignores detections, as it ignores flags.
- **R2.4.1 (after trying it on staging, 2026-11-05):** PRD E8 is applied as "a new version replaces the old ones":
  saving a version, or turning a rule off, withdraws the older versions' open suspects; decided detections keep
  their version (migration 0006 removed the 237 leftovers on staging). Rules that never raised anything can be
  deleted (`DELETE admin/rules/{id}`, audited); versions never. The editor shows which version is in effect and
  what each changed, warns about site and all-sites overlaps, and the dry run counts stretches other rules of the
  field already raised. Direction proposals stay within 0–360°.

### 4.5 Records and calibration (R2.5)

- Metadata columns on `system`, `site` and `component` as listed in FR-REG-004, with the PRD's validation
  (coordinates, dates not in the future, 4-letter ICAO code). Serial and part numbers are Viewer-level.
- `calibration_record` (component, date, performed by, certificate number, next due date or interval, notes).
  Status is derived on read: OK, due soon (window from Settings, default 30 days), overdue, unknown.
- Overdue components become a Problems item (minor).
- **R2.5 as built (screens approved 2026-11-05):** migration 0007 adds the record columns (all optional, with the
  PRD's checks in the database too) and `calibration_record` (date, performed by, certificate, next due date,
  interval in months 1–120, notes, created / updated / removed by and at; `next_due > date`). The status is
  derived on read from the latest record not removed (`simola/records.py`, pure and unit-tested): overdue from the
  day after the due date, due soon within `calibration_due_soon_days` (setting, 1–180, default 30), unknown
  without a record; DCPs are never calibrated. An interval gives the same day that many months later, or the
  month's last day. Removing a calibration is a soft delete (kept forever, PRD §9.6). The public `assets` page
  leaves out serial and part numbers; the security check fails if either reaches a public response. The figure
  trace (FR-AUD-003, Viewer+) is read from the audit log (flags on the component, decisions on its
  mandatory-field detections, mandatory-field changes of its type, its in-service changes) and the job table
  (reprocess and recompute jobs over the period). Nothing in R2.5 changes a figure, so nothing is recomputed.
- **R2.5.1 (PO, 2026-11-06):** a calibration can be done before its certificate is validated. Migration 0008 adds
  `calibration_record.validated_on` (optional, not before the calibration date); empty = certificate pending,
  shown next to the status everywhere it appears. The next due date still counts from the calibration date.
  `simola import-records` loads records and calibrations from a JSON file through the same checks and audit as
  the screens (all or nothing, repeatable), used for the station's installation dates and the December 2025
  calibration.

### 4.6 API additions

All under `/api/v1`. Writes need a session and the CSRF header.

| Area | Endpoints | Role |
|---|---|---|
| Session | `POST auth/login`, `POST auth/logout`, `GET auth/me`, `POST auth/password` | any / logged in |
| Users | `GET/POST admin/users`, `PATCH admin/users/{id}` (role, active, reset password) | Admin |
| Audit | `GET admin/audit` (filters, `?format=csv`) | Admin |
| Jobs | `GET/POST admin/jobs`, `POST admin/jobs/{id}/cancel`, `GET admin/jobs/{id}/log` | Admin |
| Settings | `GET/PUT admin/settings/{key}` (validated per key) | Admin |
| Registry | `GET/PUT admin/mandatory-fields/{component type}`, `PATCH admin/components/{id}` (in service, metadata) | Admin |
| Flags | `GET flags?scope&from&to` (reason for everyone; note and author for Viewer+), `POST/PATCH/DELETE admin/flags` | public read / Admin write |
| Detections | `GET detections?status=…` (confirmed: everyone; suspect and rejected: Viewer+), `POST admin/detections/decide` (bulk) | public/Viewer read / Admin write |
| Rules | `GET/POST admin/rules`, `PUT admin/rules/{id}` (new version) | Admin |

| Trace (R2.5) | `GET systems/{code}/trace?scope=component:…&from&to` | Viewer |

### 4.7 Screens

- **Top bar:** a "Sign in" link for the public; after sign-in, the user's name with "Change password" and "Sign out";
  an **Admin** menu for Admins next to the system menus.
- **Admin area** (`/admin`): one page with a side list of the PRD's sections: review queue, flags, rules,
  mandatory fields, registry and calibration, settings, jobs, users, audit log, system health.
- **Flagging where the problem is seen:** select a time range on a sensor chart or in the minute map, then
  "Flag…" opens a short form (components, reason, note) with the minutes it will affect.
- **Charts:** confirmed flags and detections shaded with their reason; suspects in a lighter, dashed style for
  Viewers and Admins only. The public sees the reason category; notes and who flagged are for Viewers and Admins,
  since a note may mention internal details.
- **Minute map:** adds flagged, confirmed detection and suspect states with links.
- Indonesian and English for every new text, as in R1.

### 4.8 Security testing (R2.1 onward)

- **Permission matrix:** an automated test calls every API route as public, Viewer and Admin and checks the result
  against §5.4 (FR-AUTH-005). A new route without an entry fails the test.
- Session: cookie flags, logout invalidates, session fixation, idle and absolute expiry.
- CSRF rejected without the header; lockout and per-address limit; no username enumeration.
- Audit entries cannot be changed or deleted by the application role.
- `tools/security_check.py` gains the account checks; CI's ZAP job adds a scan as a logged-in Viewer.

### 4.9 Database changes

New numbered migrations (`0003_accounts_audit.sql` …), each additive and compatible with the previous release
(NFR-OPS-002), so a rollback to R1 code still runs. R1's figures need no data migration.

## 5. Branches and environments

- Each phase is built on its own branch (`r2.1-accounts`, …) with CI on every push (unit, integration against a
  throwaway database, browser tests on sample data). Screens are approved from screenshots before building (D3).
- When a phase is complete and green, it merges into `main` and goes to staging (D1), then to production with the
  next production deploy. The January cutover deploys `main` as it is then, R1 plus the R2 phases accepted on
  staging; the cutover runbook is updated for whatever that includes (for example Access per D4 once R2.1 is in).
- **Keeping December verifiable:** the acceptance recount (`tools/recount.py --daily`) counts the raw files and knows
  nothing about flags or detections. So until R1 is accepted, staging holds **no flags or confirmed detections in
  December or in the two reference months**. Test flags and detections (U3, U4) go on other months and are removed
  after the test; the recount then matches again, which is itself part of U4.
- After each deploy, the per-day recount on staging must still match every day.

## 6. Risks

| Risk | Mitigation |
|---|---|
| Flags or detections shift R1 figures by mistake | One validity clause (§4.3); per-day recount must match with no flags; U4 checks exact minutes |
| Full-history detection is slow on 4 shared CPUs | Window-function SQL per month, run as a job; measured against the 30-min target before R2.4 ships |
| Login exposed to the internet | Lockout, per-address limit, Cloudflare in front, Access kept on `/admin` (D4) |
| Admins lose access (forgotten password, last Admin locked) | The bootstrap command can reset an Admin from the server; the last active Admin cannot be deactivated |
| R2 scope grows | This document is the scope; new ideas go to R3 or later unless you swap something out |

## 7. Acceptance (PRD §15.8)

Every R2 **Must** implemented with its acceptance criteria passing; CI green, including the permission matrix and
security tests; UAT **U3, U4, U5** signed off; runbooks and `.env.example` updated; recount still exact.
